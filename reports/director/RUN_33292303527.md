## Summary

The audit returned `repair` for V2-00. The greenfield architecture is sound — domain/application/infrastructure/UI separation, honest local adapters, coherent visual design, 66 passing tests, and successful JS bundle/prebuild. However, two `mustFix` findings block acceptance.

## Findings to Repair

### mustFix #1 — Expo Package Version Mismatch

**Problem:** Package versions were guessed with the old Expo version scheme (`expo-constants ~17.0.3`, `expo-font ~13.0.4`, etc.) instead of using SDK 57 aligned versions. This causes native Android compilation failure (`./gradlew :app:assembleDebug` → `BUILD FAILED` on `expo-constants:compileDebugKotlin`).

**Fix required:** Replace all guessed Expo package versions with SDK 57 aligned versions via `npx expo install` or by pinning to the versions from `expo/bundledNativeModules.json`. Regenerate lockfile. Verify native compilation.

**Verification:** `./gradlew :app:assembleDebug` succeeds; `npx expo install --check` reports no misaligned packages; `npm run check` remains green.

### mustFix #2 — Analytics Leaks Operational ID

**Problem:** `ChoreScoreApp.createEntry` emits `householdId` in the analytics fact's `data` field, violating:
- The port contract (`ResearchAnalyticsGateway`: "Never include: userId, householdId, memberId, email, free text, IP, device ID")
- The `DATA_PRODUCT_PRIVACY.md` policy (no operational identifiers in analytics)

**Fix required:** Remove `householdId` (and any other operational IDs) from the analytics fact emitted by `createEntry`. Retain only minimized/aggregated data (duration, beneficiary count, persistent task presence). Add a test exercising `createEntry` with analytics enabled that asserts the absence of all operational IDs.

**Verification:** A test exercising `ChoreScoreApp.createEntry` with analytics enabled verifies the fact contains no `householdId`, `memberId`, `label`, or other operational identifier.

### Non-blocking (deferred to V2-01)

`createHousehold` passes the literal string `'new-household'` as `householdId` for entitlement checks. This is semantically incorrect (the household doesn't exist yet at creation) and will be addressed when V2-01 restructures entitlement resolution at the account level.
