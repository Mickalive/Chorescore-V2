## Findings

### 1. `mustFix` — Versions de paquets Expo devinées → compilation native Android en échec

**Path :** `package.json`

**Problème :** La tâche demandait explicitement de « laisser Expo aligner ses paquets compatibles plutôt que deviner des versions ». Le builder a au contraire épinglé plusieurs paquets Expo avec l'**ancien schéma de versionnage** :

| Paquet | Attendu SDK 57 (`bundledNativeModules.json`) | Épinglé par le builder | Installé |
|--------|----------------------------------------------|------------------------|----------|
| expo-constants | ~57.0.16 | ~17.0.3 | 17.0.8 |
| expo-font | ~57.0.2 | ~13.0.4 | 13.0.4 |
| expo-splash-screen | ~57.0.8 | ~0.30.3 | 0.30.10 |
| expo-linking | ~57.0.8 | ~7.0.3 | 7.0.5 |
| expo-status-bar | ~57.0.1 | ~2.2.3 | 2.2.3 |
| expo-router | ~57.0.17 | ~4.0.4 | 4.0.22 |
| react-native-safe-area-context | ~5.7.0 | ~5.4.0 | 5.4.1 |

**Conséquence :** la compilation native Android échoue. `./gradlew :app:assembleDebug` → `BUILD FAILED` sur `:expo-constants:compileDebugKotlin` :
```
e: ConstantsModule.kt:13:35 Unresolved reference 'constants'.
e: ConstantsService.kt:20:6 Class 'ConstantsService' is not abstract and does not implement abstract members:
val constants: Map<String, Any?> ...
```
`expo-constants` 17.0.8 est incompatible avec `expo-modules-core` 57.0.14 installé. L'APK ne peut pas être construit. C'est une « dépendance incorrecte » au sens de la mission de l'Auditor.

**Preuve :** sortie gradle ci-dessus ; comparaison `package.json` vs `node_modules/expo/bundledNativeModules.json`.

**Correction exigée :** remplacer les versions devinées par les versions alignées SDK 57 (via `npx expo install` ou en pinant les versions de `bundledNativeModules.json`), régénérer le lockfile, vérifier la compilation native.

**Vérification :** `./gradlew :app:assembleDebug` (ou `assembleRelease`) réussit ; `npx expo install --check` / `expo-doctor` ne signale plus de paquet hors alignement ; `npm run check` reste vert.

### 2. `mustFix` — Le fait analytics émet l'ID opérationnel `householdId`

**Path :** `src/application/use-cases/ChoreScoreApp.ts`

**Problème :** `createEntry` émet un fait analytics dont `data` contient `householdId: data.householdId`. Cela viole :
- le contrat documenté du port `ResearchAnalyticsGateway` (`src/application/ports/index.ts`) : « Never include: userId, householdId, memberId, email, free text, IP, device ID » ;
- la politique canonique `docs/DATA_PRODUCT_PRIVACY.md` : aucun identifiant opérationnel ne doit entrer dans le plan analytique.

Le test analytics existant ne détecte pas le défaut car il teste l'adapter en isolation avec un fait construit à la main, pas le chemin réel `createEntry`.

**Preuve :** test indépendant exécuté — `createEntry` avec analytics activé produit un fait dont `data` contient `householdId: "h-test"` (`expect(...).not.toHaveProperty('householdId')` échoue).

**Correction exigée :** retirer `householdId` (et tout autre identifiant opérationnel) du fait analytics ; ne conserver que des données minimisées/agrégées (durée, nombre de bénéficiaires, présence de PersistentTask). Ajouter un test qui exerce `createEntry` avec analytics activé et vérifie l'absence de tout ID opérationnel.

**Vérification :** un test exerçant `ChoreScoreApp.createEntry` avec analytics activé vérifie que le fait ne contient ni `householdId`, ni `memberId`, ni `label`, ni autre identifiant/texte libre.

### 3. Non bloquant — `createHousehold` passe la chaîne littérale `'new-household'` comme `householdId`

**Path :** `src/application/use-cases/ChoreScoreApp.ts`

**Problème :** `createHousehold` appelle `canUseFeature('new-household', 'create-household')` en passant `'new-household'` comme `householdId`. Le contrôle d'entitlement est effectué contre un ID de foyer inexistant (le foyer n'existe pas encore à la création). Le use-case n'est pas câblé à l'UI (bouton « Créer un foyer » sans `onPress`) et sera traité proprement en V2-01, mais le défaut logique est réel.

**Correction exigée :** en V2-01, restructurer la création de foyer pour résoudre l'entitlement au niveau du compte (un foyer gratuit créé/possédé, foyers supplémentaires avec leur propre plan) plutôt que contre un ID de foyer factice.

Le socle greenfield est bien posé sur le plan architectural, fonctionnel et visuel, et les tests déterministes sont verts. Cependant, deux findings `mustFix` empêchent l'acceptation :
