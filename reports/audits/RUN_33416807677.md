## 4. Must-fix findings

### Finding 1 — `getMemberPermissionLevel` grants MEMBER-level permissions to non-members

**Path:** `src/application/use-cases/ChoreScoreApp.ts`

**Problem:** `getMemberPermissionLevel` returns `'MEMBER'` for a user with **no membership** in the household:

```ts
const membership = await this.repositories.memberships.getByUserAndHousehold(userId, householdId);
if (!membership) return 'MEMBER'; // Default: no membership = member-level
```

MEMBER-level permissions include `canCreateEntry: true`. A stranger who is not a member of a household is therefore granted the ability to create entries in that household. This violates the constitution's strict tenant isolation and server-side authz requirements ("strictement isolé par tenant/foyer", "protégé par authz côté serveur"). A non-member should have **no access** to a household they do not belong to.

**Evidence:** `ChoreScoreApp.ts` line 669; `MemberPermissions.ts` MEMBER level sets `canCreateEntry: true`; test `V2-06-phase2-acceptance.test.ts` lines 1717–1720 explicitly asserts `'MEMBER'` for `'u-stranger'` in `'h-test'`.

**mustFix:** true

**Required fix:** Return a no-access/denied result (or throw) for a user with no membership, rather than defaulting to MEMBER. MEMBER-level permissions (especially `canCreateEntry`) must only be granted to actual household members. Update the test to assert the correct no-access behavior.

### Finding 2 — `getConflictLog` violates tenant isolation

**Path:** `src/infrastructure/local/LocalSyncAdapter.ts`

**Problem:** The conflict log is not tenant-scoped:

```ts
getConflictLog(_householdId: string): ConflictResolution[] {
  return Array.from(this.conflictLog.values()).flat();
}
```

`getConflictLog` ignores the `householdId` parameter and returns **all conflicts across all households** flattened. Additionally, `logConflict` derives the household key from `resolution.entityId.split('-')[0]` (for `entityId: 'e-1'` it derives `'e'`), which is a bogus key that does not correspond to any real household. This breaks the per-household isolation invariant that each household's sync state and audit data must be scoped to that household.

**Evidence:** `LocalSyncAdapter.ts` lines 145–147 and line 138. Test line 1543 calls `getConflictLog('h-test')` and expects length 1, which only passes because the method returns all households' conflicts regardless of the requested household.

**mustFix:** true

**Required fix:** Make `logConflict` accept an explicit householdId (or derive it correctly from the queued change context) and make `getConflictLog(householdId)` return only that household's conflicts. Add a two-household isolation test.

---

### Finding 3 — `getPendingInvitations` semantic mismatch (userId vs email)

**Path:** `src/application/use-cases/ChoreScoreApp.ts` + `src/infrastructure/local/LocalInvitationAdapter.ts`

**Problem:** The app-level `getPendingInvitations(userId)` is documented as taking a **userId** but passes it directly to the adapter's `getPendingInvitations(userIdOrEmail)`, which matches against `invitedEmail`. For a real userId (e.g. `'u-1'`) the adapter does `invitedEmail.includes('u-1')`, which never matches a real email — so the documented userId-based API is functionally broken. The adapter also uses substring `includes` matching, which is a privacy risk (a short query string can match multiple unrelated emails).

**Evidence:** `ChoreScoreApp.ts` lines 767–770; `LocalInvitationAdapter.ts` lines 83–90. The test (line 1768) masks the bug by passing an email string directly to `app.getPendingInvitations`.

**mustFix:** true

**Required fix:** Resolve the user's email from the userId before matching invitations (or have the adapter look up invitations by userId), and replace substring `includes` matching with exact email matching to avoid privacy leaks. Update the test to exercise the userId-based API correctly.
