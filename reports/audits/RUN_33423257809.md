## 3. Verification of the three must-fix repairs

### MF-1 — `getMemberPermissionLevel` must deny non-members

**Pristine:** `if (!membership) return 'MEMBER';` — granted MEMBER-level permissions (including `canCreateEntry`) to strangers with no membership.

**Candidate:**
```ts
const membership = await this.repositories.memberships.getByUserAndHousehold(userId, householdId);
if (!membership) {
  throw new Error('User is not a member of this household');
}
```

Non-members are now denied (throw) instead of being granted MEMBER. This restores deny-by-default and strict tenant isolation / server-side authz.

**Test:** `V2-06-phase2-acceptance.test.ts` lines 1762–1769 ("should resolve default MEMBER for non-member") now asserts that `getMemberPermissionLevel('u-stranger', 'h-test')` throws with message containing `'not a member'`. ✓ **Fixed.**

### MF-2 — `logConflict`/`getConflictLog` must be household-scoped

**Pristine:** `logConflict(resolution)` derived a bogus key from `resolution.entityId.split('-')[0]`; `getConflictLog(_householdId)` returned `Array.from(this.conflictLog.values()).flat()` — all households' conflicts regardless of the requested household.

**Candidate:**
```ts
logConflict(householdId: string, resolution: ConflictResolution): void {
  const log = this.conflictLog.get(householdId) ?? [];
  log.push(resolution);
  this.conflictLog.set(householdId, log);
}
getConflictLog(householdId: string): ConflictResolution[] {
  return [...(this.conflictLog.get(householdId) ?? [])];
}
```

`logConflict` now takes an explicit `householdId` and stores under that key; `getConflictLog(householdId)` returns only that household's conflicts (empty for unknown households). The bogus key derivation and the all-households flatten are removed.

**Test:** lines 1534–1580 ("should log conflict resolutions", "should isolate conflict logs between two households") log conflicts for `h-test` and `h-other`, then assert each household sees only its own conflict and an unknown household returns empty. ✓ **Fixed.**

### MF-3 — `getPendingInvitations` must resolve userId to email and use exact matching

**Pristine:** app-level `getPendingInvitations(userId)` passed the userId directly to the adapter, which matched against `invitedEmail` with substring `includes` — functionally broken for real userIds and a privacy risk.

**Candidate (app):**
```ts
async getPendingInvitations(userId: string): Promise<Invitation[]> {
  if (!this.services.invitations) return [];
  const user = await this.repositories.users.getById(userId);
  if (!user) return [];
  return this.services.invitations.getPendingInvitations(user.email);
}
```

**Candidate (adapter):**
```ts
async getPendingInvitations(email: string): Promise<Invitation[]> {
  return Array.from(this.invitations.values()).filter(
    inv => inv.status === 'pending' && inv.invitedEmail === email
  );
}
```

The app resolves `userId` → `user.email` via the user repository, then passes the email to the adapter, which uses exact `===` matching (substring `includes` removed).

**Tests:** lines 1804–1819 ("should get pending invitations via userId (resolves to email)") seeds a user with a known email, creates an invitation to that email, and calls `app.getPendingInvitations('u-pending')` expecting a match; lines 1821–1836 ("should not match invitations by substring") seeds a partial-match user and asserts it sees 0 invitations. ✓ **Fixed.**
